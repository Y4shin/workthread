# Research: logic that must run between the writes of one transaction

## Summary

The literature puts the logic inside the transaction boundary, not outside it: either a procedure that reads and writes as it goes (Transaction Script, Service Layer holding the transaction), or a Unit of Work that records decisions the domain already made and flushes them at the end. The pure decider shape (`decide(state, command) -> changes`) is the one shape that deliberately keeps the decision out of the transaction, which is exactly why it cannot decide on state the writes just produced. For a port that hides the connection, the mid-transaction decision is only expressible by a callback or by a function-valued change record; there is no third option, and the honest recommendation is to make that function a value inside the change set.

## Findings

### 1. What the domain-model literature says

1. **Unit of Work is the canonical "collect then write" shape, and it does not carry decisions.** Fowler defines it as the object that "maintains a list of objects affected by a business transaction and coordinates the writing out of changes and the resolution of concurrency problems." His stated rationale is that writing on every change "requires you to have a transaction open for the whole interaction," while a Unit of Work "keeps track of everything you do during a business transaction that can affect the database" and at the end "figures out everything that needs to be done to alter the database as a result of your work." The unit of work is a mutable registry, not a data value: the caller registers its objects against it and the domain objects keep mutating while the transaction is open. **Sources:** [Unit of Work](https://martinfowler.com/eaaCatalog/unitOfWork.html). **Support:** direct evidence. **Confidence:** high.

2. **Transaction Script is the shape where logic interleaves reads and writes on purpose.** It "organizes all this logic primarily as a single procedure, making calls directly to the database or through a thin database wrapper." Each request gets its own script, and "common subtasks can be broken into subprocedures." There is no separation between the step that decides and the step that writes; the procedure does both, in order, inside one transaction. **Sources:** [Transaction Script](https://martinfowler.com/eaaCatalog/transactionScript.html). **Support:** direct evidence. **Confidence:** high.

3. **Repository plus Service Layer puts the transaction boundary on the service method.** Service Layer "encapsulates the application's business logic, controlling transactions and coordinating responses in the implementation of its operations." Repository "mediates between the domain and data mapping layers using a collection-like interface for accessing domain objects," which is the interface that lets the service read and mutate without seeing the mapper. The composition is: service method opens the transaction, calls repositories and domain methods in any order it likes, and the transaction closes when the method returns. **Sources:** [Service Layer](https://martinfowler.com/eaaCatalog/serviceLayer.html), [Repository](https://martinfowler.com/eaaCatalog/repository.html). **Support:** direct evidence for the definitions, interpretation for the composition. **Confidence:** high.

4. **The aggregate is the unit that defines where synchronous consistency is allowed.** Evans: "Cluster the entities and value objects into aggregates and define boundaries around each ... Define properties and invariants for the aggregate as a whole and give enforcement responsibility to the root or some designated framework mechanism. Use the same aggregate boundaries to govern transactions and distribution. Within an aggregate boundary, apply consistency rules synchronously." **Sources:** [DDD Reference, p. 16](https://domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf). **Support:** direct evidence. **Confidence:** high.

5. **The decider separates the decision from the state change, and is explicitly pure.** Chassaing: `type Decide = Command -> State -> Event list`, and "This function has no reason to produce any side effects, such as reading or writing external state, or calling external services ... It can be implemented as a pure function." The state is a parameter, supplied by the caller. Axon documents the same split as a framework contract: `@CommandHandler` methods are "the place where you would put your decision-making/business logic," while `@EventSourcingHandler` methods are "where all the state changes happen." **Sources:** [Functional Event Sourcing Decider](https://thinkbeforecoding.com/post/2021/12/17/functional-event-sourcing-decider), [Axon Framework, Aggregates](https://docs.axoniq.io/axon-framework-reference/4.13/axon-framework-commands/modeling/aggregate/). **Support:** direct evidence. **Confidence:** high for the quoted wording; medium for treating Chassaing as the naming origin, since that post is a first-party design essay rather than a specification.

6. **Researcher inference.** Ranged against the concrete port, these answers split in two. Unit of Work and Transaction Script both assume the logic has the connection's transaction in scope, which the port forbids. The decider assumes the state is already fully readable before the decision, which the port's open question violates. So the literature does not hand over a ready-made answer for "connection-free port plus mid-transaction decision"; it hands over a trade-off between the two families.

### 2. How the concrete Java layers let code run between writes

1. **jOOQ: logic runs in the lambda, which receives a derived `Configuration`.** `create.transaction((Configuration trx) -> { ... })`; the manual notes the lambda "receives a new, derived configuration which should be used within the local scope" and warns to "avoid using the scope from outside the transaction." Commit is implicit at the end of the lambda; "any uncaught checked or unchecked exception thrown from your transactional code ... will rollback the transaction." Nested calls create savepoints rather than new transactions. Reads issued through `trx.dsl()` sit on the same connection as the earlier writes, so they observe them. **Sources:** [jOOQ manual, Transaction management](https://www.jooq.org/doc/latest/manual/sql-execution/transaction-management/). **Support:** direct evidence for the handle, commit, and rollback rules; interpretation for read visibility, since the manual does not state it in those words. **Confidence:** high for the API shape, medium for the visibility statement.

2. **Jdbi: logic runs in the `inTransaction` callback.** "The `inTransaction` and `useTransaction` methods on the `Jdbi` object create a new `Handle`, open a transaction and pass it to the callback code." At the end of the callback the transaction commits if no exception was thrown and nobody called `rollback()`. Nested `inTransaction` on an open transaction reuses it rather than nesting. Jdbi also states the visibility rule outright: "JDBC has one transaction per connection. When a statement executes outside of a Jdbi transaction and a Jdbi transaction then commits on the same connection, the commit includes the earlier statement." **Sources:** [Jdbi 3 Developer Guide, 11.1 Managed Transactions](https://jdbi.org/#_managed_transactions). **Support:** direct evidence. **Confidence:** high.

3. **JPA and Hibernate: no callback; logic runs in the service method and the flush happens later.** State changes accumulate in the persistence context (dirty checking) and reach the database at flush time, at the latest at commit. What makes reads inside the method correct is `FlushModeType.AUTO`: "the persistence provider is responsible for ensuring that all updates to the state of all entities in the persistence context which could potentially affect the result of the query are visible to the processing of the query ... The persistence provider implementation may achieve this by flushing those entities to the database or by some other means." With `COMMIT`, "the effect of updates made to entities in the persistence context upon queries is unspecified." So the answer to "do reads see earlier writes" is yes under the default mode and explicitly not guaranteed under `COMMIT`. **Sources:** [Jakarta Persistence 3.1, FlushModeType](https://jakarta.ee/specifications/persistence/3.1/apidocs/jakarta.persistence/jakarta/persistence/FlushModeType.html). **Support:** direct evidence. **Confidence:** high.

4. **Spring `@Transactional`: the transaction is bound to the thread and shared by every data access call in the method.** "`@Transactional` commonly works with thread-bound transactions managed by `PlatformTransactionManager`, exposing a transaction to all data access operations within the current execution thread." That is what makes "write, then read, then decide, then write" work in a service method: all the calls join one transaction. Two documented traps matter for a port design: in proxy mode "self-invocation ... does not lead to an actual transaction at runtime even if the invoked method is marked with `@Transactional`," and the default rollback rule is "Any `RuntimeException` or `Error` triggers rollback, and any checked `Exception` does not." **Sources:** [Spring Framework, declarative transaction implementation](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-decl-explained.html), [Spring Framework, Using @Transactional](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html). **Support:** direct evidence. **Confidence:** high.

5. **SQLite: the transaction is serializable, but a snapshot read outside the write transaction goes stale.** "Except in the case of shared cache database connections with PRAGMA read_uncommitted turned on, all transactions in SQLite show serializable isolation. SQLite implements serializable transactions by actually serializing the writes. There can only be a single writer at a time." And in WAL mode, "any write transactions that commit while the read transaction is active are still invisible to the read transaction"; to see them, the reader "must end its read transaction and start a new one," and an attempt to escalate a stale read transaction to a write "fails with an SQLITE_BUSY_SNAPSHOT error." **Sources:** [Isolation In SQLite](https://www.sqlite.org/isolation.html). **Support:** direct evidence. **Confidence:** high. **Why it matters here:** any decision taken from a read performed before `applyAll` is a decision on a snapshot, not on the state the transaction will write over.

### 3. Named alternatives to a callback at the port boundary

Two things first. Only two families exist: read the state before the call and pass a decision (decider), or pass something the adapter can evaluate later (function or callback). Everything below is a variation on one of the two.

1. **Decider function, `decide(state, command) -> changes`.** The port gains a read method plus `applyAll`. The core reads, calls `decide`, then calls `applyAll`.
   - Expresses: any rule over the state as read, in a pure and trivially testable function, with no adapter ordering detail leaking into the core.
   - Cannot express: anything that depends on a value produced by an earlier change in the same set, and anything that depends on rows another writer changed between the read and the write.
   - Cost at the fake: nearly zero, and it is a strength. The fake reads its map, calls the same `decide`, applies the returned data. The fake and the adapter share the decision code, so the test asserts on the domain function, not on the adapter.
   - Sources: [Decider](https://thinkbeforecoding.com/post/2021/12/17/functional-event-sourcing-decider), [Axon, Aggregates](https://docs.axoniq.io/axon-framework-reference/4.13/axon-framework-commands/modeling/aggregate/). **Support:** direct evidence for the shape and its purity; the expressiveness limits are interpretation. **Confidence:** high.

2. **A computed change case, `Deferred(Function<View, List<Change>>)`, evaluated by the adapter inside the transaction.** One element of the change set is a function plus the identity of what it needs to see. The adapter builds `View` from the same connection, mid-set, and appends the returned changes to the ones already applied.
   - Expresses: decisions from state that exists part-way through the set, including state the set itself just wrote, because the adapter supplies the view at the right moment.
   - Cannot express: anything needing an answer from outside the port, anything needing a branch on failure mid-set (the abstraction can only abort the whole set), and anything needing a fixpoint loop over unknown rounds.
   - Cost at the fake: it must implement `View` by reading its own map after applying the earlier changes, and it must apply changes one at a time in order instead of swapping a whole map. The function must be side-effect free and re-runnable, because the adapter may evaluate it more than once after a retry. In practice the fake gains one small class and loses the ability to assert a change set by structural equality alone.
   - Support: no primary source names this variant. **Researcher inference**, with the JDK `ConcurrentMap` contract as the closest first-party analogy (see item 4).

3. **Expected-state or compare-and-set precondition on a change.** A change carries what it expects to be true (`expect no task in progress`, `expect row version 7`). The adapter turns it into a guarded write and fails the set if the guard did not match.
   - Expresses: "this decision was made against state X, apply only if state is still X", which is exactly the lost-update defence. It also expresses joint validity cheaply: two guarded writes that are individually illegal but jointly legal can be applied and then checked once at the end of the set.
   - Cannot express: computing a value from the row the transaction just wrote. A precondition is a filter, not a read.
   - Cost at the fake: small. The fake checks the same predicate against its own state, which is a map lookup; the real cost is that the fake must reproduce the same comparison semantics (what counts as "the same row"), and every such predicate is one more thing that can drift between fake and adapter.
   - Sources: [Optimistic Offline Lock](https://martinfowler.com/eaaCatalog/optimisticOfflineLock.html), [Jakarta Persistence, `@Version`](https://jakarta.ee/specifications/persistence/3.1/apidocs/jakarta.persistence/jakarta/persistence/Version.html), [jOOQ optimistic locking](https://www.jooq.org/doc/latest/manual/sql-execution/crud-with-updatablerecords/optimistic-locking/), [SQLite `sqlite3_changes()`](https://www.sqlite.org/c3ref/changes.html) for how the guard's effect is detected (row count zero). **Support:** direct evidence for the pattern and the mechanisms; the "cannot express" line is interpretation. **Confidence:** high.

4. **Read-modify-write operation taking a function, `modify(Subject, Function<State, List<Change>>)`.** A port method scoped to one subject: the adapter reads that subject inside the transaction, hands the state to the function, applies what comes back.
   - Expresses: read-decide-write for one subject, with no view type exposed and no change set built up front. This is the shape of `ConcurrentMap.compute`.
   - Cannot express: a decision that spans several subjects (for example "start this task only if no other task is in progress" needs the set of tasks, not one task), and a decision that depends on a value the write itself generates.
   - Cost at the fake: lowest of the function-bearing options. `compute` over a map is the fake, literally. The JDK contract also states the price of any such shape in one sentence: "When multiple threads attempt updates, map operations and the remapping function may be called multiple times," and "The remapping function should not modify this map during computation." A function that is passed to an adapter must be pure for the same reason.
   - Sources: [Java SE 21, ConcurrentMap](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ConcurrentMap.html). **Support:** direct evidence for the JDK contract, interpretation for the port mapping. **Confidence:** medium (the mapping is mine; the contract is not).

5. **One more declarative escape hatch, worth naming.** Some mid-set decisions need no function at all because a single SQL statement can perform the read and the write together: a conditional `INSERT ... WHERE NOT EXISTS`, or `UPDATE ... WHERE <predicate>` with a row-count check. SQLite's `RETURNING` also answers "compute a value from the row just written" without a second statement: "For INSERT and UPDATE statements, references to columns in the table being modified refer to the value of that column after the change has been applied." This only covers decisions whose whole logic fits in one statement. **Sources:** [SQLite RETURNING](https://www.sqlite.org/lang_returning.html), [SQLite `sqlite3_changes()`](https://www.sqlite.org/c3ref/changes.html). **Support:** direct evidence. **Confidence:** high for the mechanism, medium for how far it stretches in this codebase.

### 4. Decisions made on state the transaction just wrote

1. **Plainly: without a callback or a function-valued change, such a decision cannot be made.** A data-only change set is fixed before the call, so every decision inside it was taken against state read before the call. Adding preconditions changes whether the set is accepted, not what the set computes. **Researcher inference**, but a direct consequence of the definition of a value: nothing in a constant can depend on a later write.

2. **The literature agrees by construction.** The decider is pure and takes state as a parameter, so it cannot read. Unit of Work assumes the domain already holds the live objects and mutates them while the transaction is open, which is the connection-scoped behaviour the port forbids. Transaction Script has the connection in scope by definition. **Sources:** [Unit of Work](https://martinfowler.com/eaaCatalog/unitOfWork.html), [Transaction Script](https://martinfowler.com/eaaCatalog/transactionScript.html), [Decider](https://thinkbeforecoding.com/post/2021/12/17/functional-event-sourcing-decider). **Support:** interpretation of direct quotes. **Confidence:** high.

3. **The workable middle ground is to choose which decisions are read-before and which are read-inside.** A decision over state that no other writer touches inside the set can be a decider call. A decision over state the set itself writes has to be either a function-valued change or a guarded write that pushes the decision into SQL. Enumerating the core's use cases against those three buckets is the real design work, not choosing a port signature.

### 5. What the sources say about correctness

1. **A decision made on a pre-read state needs validation inside the writing transaction, or it races.** Fowler: "Often a business transaction executes across a series of system transactions. Once outside the confines of a single system transaction, we can't depend on our database manager alone to ensure that the business transaction will leave the record data in a consistent state. Data integrity is at risk once two sessions begin to work on the same records and lost updates are quite possible." And the resolution: "So long as the validation and the updates occur within a single system transaction the business transaction will display consistency." This is the sentence that decides the question: the validation has to travel with the update, which is what a precondition on a change is for. **Sources:** [Optimistic Offline Lock](https://martinfowler.com/eaaCatalog/optimisticOfflineLock.html). **Support:** direct evidence, confirmed verbatim against the page. **Confidence:** high.

2. **Version and timestamp checks are the standard implementation of that validation.** jOOQ: with optimistic locking enabled, "Prior to UPDATE or DELETE statements, jOOQ will run a SELECT .. FOR UPDATE statement, pessimistically locking the record," comparing the fetched data with the record, and "An `org.jooq.exception.DataChangedException` is thrown if the record had been modified or deleted in the meantime." With a version or timestamp column it instead "adds a WHERE-clause to the UPDATE or DELETE statement, checking for TIMESTAMP's integrity." Jakarta Persistence states the field's purpose: the `@Version` property "serves as its optimistic lock value ... used to ensure integrity when performing the merge operation and for optimistic concurrency control." **Sources:** [jOOQ optimistic locking](https://www.jooq.org/doc/latest/manual/sql-execution/crud-with-updatablerecords/optimistic-locking/), [Jakarta Persistence, `@Version`](https://jakarta.ee/specifications/persistence/3.1/apidocs/jakarta.persistence/jakarta/persistence/Version.html). **Support:** direct evidence. **Confidence:** high.

3. **A decision made inside the transaction avoids the lost update only if the transaction is serializable, and it is retried on conflict.** Jdbi's own worked example is a lost update. Two transactions each read `sum(ints)` and insert it: "Without serializable isolation, each transaction reads 10 and 20, and then returns 30. The final result is 30 + 30 = 60, which does not correspond to any serial execution of the transactions! With serializable isolation, one of the two transactions is forced to abort and retry." Jdbi also warns: "It is important that your transaction does not have side effects as it may be executed multiple times," and its `SerializableTransactionRunner` retries up to 5 times by default. **Sources:** [Jdbi 3 Developer Guide, 11.3 Serializable Transactions](https://jdbi.org/#_serializable_transactions). **Support:** direct evidence. **Confidence:** high.

4. **SQLite supplies the serializability, with a caveat that matters for this port.** "All transactions in SQLite show serializable isolation" and "There can only be a single writer at a time," so a read-decide-write performed inside one write transaction is protected. A read performed before `BEGIN`, or inside a long read transaction, is a snapshot that will not include later commits, and escalating it fails. **Sources:** [Isolation In SQLite](https://www.sqlite.org/isolation.html). **Support:** direct evidence. **Confidence:** high.

5. **So the two shapes are equally correct, at different costs.** Decider plus precondition: two round trips, a retry loop on precondition failure, and the core owns the retry. Function-valued change inside one transaction: one round trip, no retry at the domain level, but the function must be pure and the fake must model partial application. **Researcher inference**, consistent with all four sources above.

### 6. Recommendation for this port

Keep one write method, `applyAll(ChangeSet)`, and make exactly one change record a deferred computation:

```
sealed interface Change permits NewTask, EditTask, RemoveTask, NewNote, Deferred {
    record Deferred(Function<WorkView, List<Change>> compute) implements Change {}
}
```

The adapter applies the set in order. On `Deferred` it builds `WorkView` from the same connection, inside the transaction, after the earlier changes, and splices the returned changes into the remainder of the set. `WorkView` is a core interface that exposes only reads the domain already needs (tasks in progress, the last change-log row, a task's current state). Nothing framework-shaped or driver-shaped crosses the port, so the in-memory fake stays viable.

Why this and not the decider: your examples are exactly the ones a decider cannot express. "Start this task only if no other task is in progress" is fine as a decider call if nothing in the set changes task state, and wrong the moment something in the same set does. "Compute a value from the row just written" and "two writes that are each invalid alone and valid together" both need the post-write view. A decider plus preconditions can cover the first, but not the second, and it moves the retry loop into the core, which is more code than one function-valued case.

Cost at the fake: it implements `WorkView` over its own collections and applies changes one at a time so that a `Deferred` sees the earlier ones. That is roughly one extra class plus a loop, and it means the fake can no longer be a single "replace the map" swap. The recomputation contract is the real constraint: `compute` must be a pure function of `WorkView`, so a fake that evaluates it twice still matches the adapter.

Inexpressible under this recommendation: branching on a mid-set failure (the set aborts as a whole, there is no "if this write failed, do that instead"), fixpoints over an unknown number of rounds, decisions that must see another connection's uncommitted work, and any read that needs a different consistency point than the transaction the adapter opened. If a use case needs one of those, it needs a second port method, not a bigger `Deferred`.

What this recommendation makes harder to reason about is the log: one change-log row per change is no longer enumerable before the call, so the log row set is only knowable after the set runs. If the change log is a contract, the `Deferred` result must be logged too, which it will be if the adapter logs while applying rather than after.

## Contradictions

1. **The decider literature forbids what the port needs.** Chassaing requires the decision to be pure and to take state as a parameter; the port's open question requires reading state mid-transaction. Not a factual conflict, but the two cannot both be satisfied by a plain `decide(state, command)`. Recorded rather than resolved.
2. **Jakarta Persistence wording changed between versions.** The 3.1 enum constant for `AUTO` reads "(Default) Flushing to occur at query execution", while the current nightly API doc reads "Pending modifications ... are automatically flushed to the database when the transaction commits." Both descriptions are consistent with flush-at-commit plus flush-before-query, but the emphasis differs. This note cites the 3.1 page, which is what I fetched and verified.
3. **jOOQ documents two mechanisms under one feature name.** `executeWithOptimisticLocking` first describes a pessimistic `SELECT ... FOR UPDATE`, then a version/timestamp `WHERE` clause. They have different failure modes and different costs, and the manual does not say which applies when both a version column and the setting are present.
4. **"Serializable" carries two meanings across the sources.** SQLite means "serialized writes, one writer at a time"; Jdbi's example means "one transaction aborts and retries on serialization failure". Both give the same guarantee, but only the second comes with a retry loop, and only the second needs side-effect-free logic.

## Missing evidence

1. No primary source states, in words, that a read on the same connection inside an open SQLite transaction sees that transaction's earlier uncommitted writes. I inferred it from "JDBC has one transaction per connection" (Jdbi) and from the isolation page describing cross-connection visibility only. Treat the visibility claim as solid engineering knowledge, not as a cited fact.
2. No primary source names the "change record carrying a function evaluated inside the transaction" pattern. It is my construction from the JDK `ConcurrentMap` contract plus the callback shapes in jOOQ and Jdbi. Nothing in the literature I checked gives it a name or a known failure catalogue.
3. I did not read the full P of EAA chapters (paywalled); only the catalog abstracts, which are short. Claims about Unit of Work internals beyond the abstract are not in this note.
4. I did not verify whether jOOQ's `SELECT ... FOR UPDATE` path works on the SQLite dialect. SQLite's `SELECT` grammar has no `FOR UPDATE`, so that path may be unusable here, which would make the version/`WHERE`-clause variant the only jOOQ optimistic-locking option. Unverified.
5. No evidence on how SQLite's single-writer lock interacts with the daemon's expected concurrency. If there is one writer process, the precondition discussion is about correctness under crashes and restarts rather than about racing writers.

## Next steps

1. Decide, per use case, which of the three buckets each mid-set decision falls into: decider on pre-read state, function-valued change, or guarded single statement. That list is the real input to the port shape.
2. Check whether the change log's ordering and content are a contract. If they are, `Deferred` must be specified to log at apply time.
3. Prototype the fake for one `Deferred` case to measure the actual cost: one `WorkView` implementation over the fake's collections, plus sequential application.
